# onboarding interview

**For: Agent**

**Bottom line:** Learn only enough confirmed context to make the next month useful. Route personal context to `life/`, shared collaboration rules to `os/`, and each business to its own repository.

**When to read this:** Read during setup or an owner-approved context refresh.

## behavior

- Ask one short section at a time and accept natural, incomplete answers.
- Explain why sensitive context would help and allow it to be skipped.
- Separate confirmed facts, preferences, hypotheses, and unknowns.
- Do not edit during discovery.
- Do not create a folder or repository for every interest, source, client, or imagined agent.
- Present the summary and exact change list before personalization.

## 1 — desired change

Learn what the owner wants the system to make easier, what repeatedly gets lost or re-explained, three useful first-month examples, and what the system must never become.

## 2 — identity and collaboration

Learn the preferred name/pronouns, stable roles, enduring constraints, response style, desired candor, manageable number of choices, and when the agent should discuss before acting. This routes to `os/me.md` and confirmed shared rules.

## 3 — current life state

Learn current priorities, deadlines, open decisions, capacity, and constraints that materially change planning. This routes to `life/now.md`, not stable identity.

## 4 — personal landscape

Learn ongoing areas, time-bound personal projects, durable knowledge needs, recurring people, capture habits, and records worth preserving. Use the existing `life/` lanes before adding subfolders.

## 5 — businesses

For each real active business, learn its name, purpose, current status, boundaries, authoritative foundations, recurring tasks, confidential data, implementation source, and whether it truly needs an independent repository now. Parked ideas remain notes; they do not become repositories.

## 6 — information and tools

Learn devices, apps, cloud drives, source-of-truth locations, import candidates, and which sources contain medical, legal, financial, client, employment, family, or third-party private data. Inventory first; never bulk-import during the interview.

## 7 — permissions and privacy

Learn approval requirements, local-edit expectations, archive policy, protected files, high-stakes boundaries, external actions, and whether the agent may commit and publish completed work under the standing Git workflow.

Never request passwords, authentication codes, recovery codes, seed phrases, private keys, API keys, or tokens.

## 8 — retrieval and routines

Learn recurring questions, current-truth locations, common stale-source
mistakes, and which routines would solve real repeated work. Ask what weekly day,
time, and time zone the owner wants for required vault maintenance; use Sunday
at 6:00 PM local when the owner has no preference. Confirm that the scheduled
routine may create verified Git checkpoints, maintain active files, archive
evidenced inactive material, and publish under the standing Git publication
workflow. Other draft routines remain available; they do not all become active
obligations.

## 9 — confirmation package

Present:

1. Stable owner profile for `os/me.md`.
2. Current snapshot for `life/now.md`.
3. Deeper owner context for `life/knowledge/people/owner.md`.
4. Collaboration, privacy, and publication rules.
5. Personal routes using the existing Life structure.
6. Each justified business repository and its starter files.
7. Source inventory and deferred-import risks.
8. Exact files and repositories that will change.
9. Whether scheduled maintenance is useful; if yes, its schedule and standing scope.
10. Important unknowns better learned through use.

Wait for the owner's explicit accuracy confirmation before editing.
